# Optimization council: state, plan and experiment log

## 1. Current state (inspected before any change)

* **Task** (HACKATHON.docx, read at the start of the project; the file is no longer on the Desktop): one
  program for classification, regression and clustering on unseen tables. 18 private datasets, 60 s each
  on one CPU environment. Score: model quality 85 (the three tasks equal), data profiling 10, speed 5
  (only credited when model performance is useful).
* **Official metric, input/output contract, checker and baseline**: released at kickoff, so **not
  available here**. The official score cannot be measured. Closest valid alternative used throughout:
  `tools/check.py` on 40 labelled practice datasets (macro-F1 / R² / ARI on hidden labels), plus the
  robustness suites `tools/stress_test{,2,3}.py` and `tools/smoke_test.py`.
* **Code**: `main.py` → `automl/io_contract.py` (load) → `profiling.py` (types, profile) →
  `preprocess.py` (tree / linear views, out-of-fold target encoding) → `relevance.py` (irrelevant
  features, wide-table screening) → `supervised.py` (CV search, greedy ensemble, decision tuning) or
  `clustering.py` (stability selection) → outputs. Watchdog, fallback and interim predictions protect
  the 60 s limit.
* **Verified working**: every practice dataset and robustness case (see the README tables).
* **Unverified**: the official contract; behaviour on the organisers' CPU; peak memory (no
  measurement existed until now; now added to `profile.json` as `peak_memory_mb`).

## 2. Council review

**A. Algorithm / domain expert**
* The approach (gradient boosting + linear + kernel + neighbour models, CV-selected greedy ensemble;
  stability-selected clustering) fits small and medium tabular data. No fundamentally better family is
  available offline in scikit-learn.
* HistGradientBoosting is the most used model, but its default hyperparameters were set by hand,
  **never tuned systematically**. This is the most promising quality lever.

**B. Senior software engineer**
* No open crash or interface bug in the test suites. Remaining risk is contract mismatch (kickoff).

**C. Performance engineer**
* Measured phase times: start-up 2–4 s (Python + pandas + scikit-learn), feature relevance 1–5 s,
  model search 5–20 s. The relevance budget (5 s) is a fixed cost on every supervised dataset.

**D. Evaluation specialist**
* Expected score impact, in order: (1) matching the official contract (not testable yet);
  (2) no timeouts or crashes (done); (3) quality, a third each for the three tasks; (4) profile
  correctness, 10; (5) speed, 5.

**E. Adversarial reviewer**
* *Leakage check*: target encoding is out-of-fold; preprocessing, relevance and screening are fitted on
  training rows only; test features are only used for clustering (no labels, allowed) and for profile
  counts. **One real bias found**: the irrelevant-feature mask used by k-NN / SVM is computed on *all*
  training rows before cross-validation, so those models' CV scores are slightly optimistic (feature
  selection outside the folds). No test labels leak, but the ensemble could over-trust those models.
* *Overfitting risk*: the practice suite was generated by us. Any tuning must be selected by
  cross-validation, not by the hidden test labels, and only kept if it generalises across datasets.
* *Noise*: results moved between runs because time-based search decisions depend on machine load
  (the laptop is often at 60–100% CPU from other programs). Repeatability has to be measured
  before small differences are believed.
